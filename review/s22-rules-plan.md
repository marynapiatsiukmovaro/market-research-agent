## 4. ⭐ МЕТОД РАБОТЫ НАД ТЕКСТОМ (Marina — подтверждаю; она назвала его сильнейшим в плане)

**Цель:** рабочий документ, где сохранены **ВСЕ строки старого `op-rules.md` дословно, с номерами строк**, и
**у каждой ушедшей фразы — свой адрес**. Это превращает «ничего не потеряно» из обещания в проверяемый факт.

**По каждому правилу, сверху вниз:**
```
П<N> — <имя>                                    [статус: оставлено / слито / дополнено / ⚠развилка]
▸ МОЯ ОБЪЕДИНЁННАЯ ФОРМУЛИРОВКА:   <чистый текст, 3–5 строк, без имён скриптов>
▸ ЧТО ДОПОЛНИЛИ и почему:          <напр. «+ старый код на тех же данных, S21»>
▸ ИЗ ЧЕГО СОБРАНО (дословно, с № строк):
   ── RULE 7 (стр. 114–118): «Confirm the hero AND the price on the LIVE site…»
   ── RULE 23 (стр. 240–259): «<дословно>»
▸ ЧТО УШЛО НЕ В ПРАВИЛО (каждая фраза — со своим адресом):
   • «(S3, Marina-approved…)» + разбор S16     → history/lessons.md
   • имена скриптов, порог reach≥90            → methods/scripts.md
   • «reach упал → products.json выключен»      → peculiarities.md §Stage 2
```
Затем **отдельный раздел «Текст, не ставший правилом»** — та же дословность + адрес (как ты показала на
Peculiarities: сверху как запишу, снизу дословная строка-источник). **Раздел важнее, чем кажется: именно там
обычно теряется ценное** (Marina).

**Где живёт документ (Marina):** эта дословная выписка = **след аудита в `review/`, НЕ в департаменте.** Иначе
вынесем из op-rules 500 строк и тут же положим рядом новые 500. **[я] След «заморожен»:** пишется ОДИН раз в
момент переноса и больше не трогается (снимок «что содержал op-rules и куда ушла каждая строка»). Приёмники —
живые. Снимок не обновляется → расходиться нечему (иначе получим те самые две поверхности, S18).

**Мои метки:** статус у каждого правила · адрес у каждой ушедшей фразы · номера строк оригинала (перепроверяемо `grep`).

## 4a. ⭐ МЕХАНИЗМ ПЕРЕНОСА: перенос = ФАКТ, а не обещание (Коворк + Marina, согласовано)

**Адрес в плане — обещание. Перенесённый текст — факт.** Вся болезнь папки — из непроверенных обещаний
(«работает, просто не задокументировано», «ридер не partial», «28 полей»). Поэтому:

- **Текст физически ложится в файл-приёмник; приёмник создаётся, если его ещё нет.** Никакого «уйдёт туда».
- **Каждый перенесённый блок несёт видимую метку источника** — откуда, из какого правила, номера строк.
  **[я] Метка машиночитаема** (единый формат, напр. `[← op-rules RULE 30 · L370–418]`), чтобы счёт по меткам
  можно было запустить регуляркой.
- **Где приёмник ещё не собран — текст ложится в явный раздел «Принято из op-rules — не обработано».**
  Одновременно верно: не потеряно (уже в целевом файле) + видно, что не встроено.
- **Файл разобран ТОЛЬКО когда этот раздел пуст** (проверяется поиском, не «мы посмотрели»).
- **[я] Приёмник создаём, но НЕ грузим сессией, пока раздел «не обработано» не пуст** — полусобранный
  `peculiarities.md` не должен попасть в обязательную загрузку посреди расчистки. Помечаем «в работе, не грузить».
- **[я] Порядок:** этап правил даёт на выходе только чистый `rules.md` + приёмники с разделами «не обработано».
  **Содержимое приёмников сейчас НЕ встраиваем** — это стадия каждого файла отдельно (там раздел и опустошается).

## 5. ⭐ МЕХАНИЧЕСКАЯ ПРИЁМКА: счёт по МЕТКАМ, а не по плану (Коворк + Marina)

Раз текст переносится С МЕТКАМИ — **счёт считается по меткам в файлах-приёмниках, а НЕ отдельным числом в
плане.** Иначе два числа могут разойтись = ровно как гейт начал врать в S18. Скрипт проходит по приёмникам,
считает метки, сравнивает с числом строк исходника:
**476 строк op-rules = правила + хроника + методы + тонкости + состояние + удалено — сумма сходится ПО ФАКТУ
переноса, а не по тому, что записали в отчёте.** **[я] Удаления тоже считаются:** чистый провенанс
(«(S6, Marina-approved)») получает метку-ветку «удалено · git помнит» — без бакета «удалено» сумма не сойдётся.

Плюс: **числа живут в ОДНОМ месте** — пороги приёмки, ценовые диапазоны, объём browse в правилах НЕ дублируются,
только ссылка (дублированный порог = как гейт начал врать в S18).
