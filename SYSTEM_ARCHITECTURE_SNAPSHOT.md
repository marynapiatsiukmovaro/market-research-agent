## 2. Product State Architecture

Products exist in distinct, non-exclusive states. A product may hold multiple states simultaneously.

### The Five States

| State | Definition | Who Sets It | Where Tracked |
|-------|-----------|-------------|---------------|
| **Reported** | Scored 65+ and surfaced by agent in a scouting session | Agent | `memory/reported-products.md` + Notion Status: Scouted |
| **Founder Approved** | Marina explicitly reviewed and validated (Approved or Consider) | **Marina only — never agent** | `memory/founder-feedback.md` + Notion Founder Review |
| **Rejected** | Failed filters, scored below 65, or founder-rejected after review | Agent (pre-score) or Marina (post-review) | `memory/rejected-products.md` + Notion Recommendation: Rejected |
| **Needs Verification** | Interesting signal but insufficient validation (missing links, unclear saturation, etc.) | Agent | Notion Recommendation: Needs Verification |
| **Calibration Example** | Used to improve future reasoning and pattern recognition | Agent or Marina (by recording feedback) | `memory/founder-taste.md`, `memory/successful-patterns.md`, `memory/failed-patterns.md` |

### State Coexistence Examples

```
Reported + Needs Verification       → surfaced by agent, but links missing or saturation unclear
Reported + Rejected (by Marina)     → agent reported it; Marina rejected it afterward
Rejected + Calibration Example      → failed, but useful as negative pattern reference
Founder Approved + Calibration      → Marina approved + strong pattern extracted from it
```

### State Separation Rules

```
Recommendation field (agent sets)     Founder Review field (Marina only)
────────────────────────────────      ──────────────────────────────────
Worth Testing                    →    (blank) awaiting Marina's review
Needs Verification               →    (blank) awaiting verification + Marina's review
Rejected                         →    (blank) Marina may confirm or override
```

**Critical rules:**
- Reported ≠ Founder Approved
- Calibration Example ≠ Founder Approved
- Needs Verification is an AI/system state, not a founder decision
- Rejected products remain in the system permanently as negative calibration
- Agent never sets Founder Review field — not even as a default

## 3. Source-of-Truth Hierarchy

When sources conflict, apply this priority order:

```
Priority 1 (OVERRIDES ALL):
  Marina's direct spoken/written feedback
  → Recorded in: memory/founder-feedback.md

Priority 2 (Calibration policy — overrides scoring):
  Founder taste rules derived from feedback
  → Recorded in: memory/founder-taste.md

Priority 3 (Hard gates — before scoring):
  Mandatory filters
  → Defined in: criteria/mandatory-filters.md

Priority 4 (Quantitative evaluation):
  Scoring system (0–100)
  → Defined in: criteria/scoring-system.md

Priority 5 (Product requirements):
  Price tiers, sourcing, creative angle minimums
  → Defined in: criteria/product-requirements.md

Priority 6 (Session execution):
  Daily scout procedure
  → Defined in: workflows/daily-scout.md
```

## 4. Scouting Pipeline (Full Sequence)

```
SESSION START
│
├── STEP 0 — Load memory
│   ├── Read memory/reported-products.md      → what was already found (anti-duplicate)
│   ├── Read memory/rejected-products.md      → patterns to skip fast
│   ├── Read memory/founder-taste.md          → Marina's bar (calibration override)
│   └── Read memory/founder-feedback.md       → real decisions (calibration rules)
│
├── STEP 1 — Scan 15–20 candidates
│   ├── Sources: TikTok Ads Library, Meta Ads Library, Amazon Movers & Shakers,
│   │            AliExpress Trending, TikTok Organic, Instagram Reels
│   └── Skip anything already in reported-products.md or rejected-products.md
│
├── STEP 2 — Apply Mandatory Filters (fast reject)
│   ├── Source: criteria/mandatory-filters.md
│   ├── Reject fast — do not score weak products
│   └── Target: 8–10 pass out of 15–20 scanned
│
├── STEP 3 — Score filtered products (0–100)
│   ├── Source: criteria/scoring-system.md
│   ├── Apply founder-taste.md calibration layer on top of score
│   └── Add competitor signal + creative angle count
│
├── STEP 4 — Find real links (for 65+ candidates)
│   ├── Find Ad/Source Link (where found)
│   ├── Find Store Link (where it sells)
│   └── If both missing → Recommendation = Needs Verification
│
├── STEP 5 — Select top products
│   ├── Minimum score: 65+
│   ├── Target: 2–5 (quality over quota — never force)
│   └── If nothing qualifies → report 0 and explain why
│
├── STEP 6 — Output Scout Mode reports
│   └── One report per product (brain/system.md format)
│
├── STEP 7 — Save to Notion
│   └── Source: workflows/notion-update.md
│       ├── Fill all agent-owned fields
│       ├── Leave Founder Review blank (Marina sets)
│       └── Leave Founder Notes blank (Marina's field)
│
└── STEP 8 — End-of-session memory update (mandatory)
    ├── reported-products.md  → add all products scored 65+
    ├── rejected-products.md  → add notable rejections with lessons
    ├── successful-patterns.md → update only if new pattern emerged
    └── failed-patterns.md    → update only if new failure pattern emerged
```

## 5. Winner Detection Logic

Signal hierarchy in order of reliability:

| Signal | Strength | Condition |
|--------|----------|-----------|
| Active Meta/TikTok ads running 14+ days straight | **Strongest** | Ad budget = proof of market (someone is getting ROI) |
| 5–30 active ads, launched 1–4 weeks ago | **Strong** | Sweet spot: proven but not saturated |
| TikTok organic growing + paid ads emerging | **Strong** | Entry window: organic → paid typically 3–8 weeks |
| Amazon BSR velocity (climbed top 50 in 30 days) | **Medium** | Demand signal, less ad-specific |
| Premium brand at $150–400 + generic attack from below | **Medium** | Market proven by proxy; generic needs visual superiority |
| WebSearch article mentions | **Weak** | Indirect — always attribute as "WebSearch mention" |

**Entry zone:** 5–30 active ads = enter. 30–100 = caution. 100+ = too late.

## 6. Calibration Layers

Three distinct calibration layers apply during evaluation:

```
Layer 1 — Hard filters (mandatory-filters.md)
  Applied first. No scoring if filter fails.
  Cannot be overridden.

Layer 2 — Numerical scoring (scoring-system.md)
  Produces 0–100 score.
  Threshold: 65+ to report, 85+ for deep validation.

Layer 3 — Founder taste calibration (founder-taste.md)
  Applied on top of numerical score.
  Can raise or lower effective bar.
  Examples:
    - Product scoring 74 with Apple-like design → "worth flagging"
    - Product scoring 78 but feels like commodity → "Maybe, low conviction"
  Source: real decisions logged in founder-feedback.md
```

**Calibration files and their levels:**

| File | Calibration Level | Updates |
|------|------------------|---------||
| `memory/founder-feedback.md` | Source (primary) | After each session, when Marina gives feedback |
| `memory/founder-taste.md` | Derived policy | When new rule pattern confirmed by multiple feedback instances |
| `memory/successful-patterns.md` | Aggregate patterns | When recurring winning trait confirmed |
| `memory/failed-patterns.md` | Aggregate patterns | When recurring failure confirmed |

## 7. Founder Feedback Flow

```
SESSION (agent reports products)
         ↓
Marina reviews in Notion
         ↓
Marina sets Founder Review: Approved / Consider / Rejected
         ↓
Marina tells agent her reasons (next session / explicit message)
         ↓
Agent records in memory/founder-feedback.md:
  - Product, Score, Marina's reason, Critical lesson
         ↓
If pattern emerges across 2+ products:
  → Update memory/founder-taste.md (policy rule)
  → Update memory/failed-patterns.md or memory/successful-patterns.md
         ↓
Next session: founder-taste.md calibrates scoring
              founder-feedback.md provides real examples
              failed-patterns.md speeds up rejection
```

**Separation rule:**
- `founder-feedback.md` = log of individual decisions (what Marina said about specific products)
- `founder-taste.md` = distilled policy (rules derived from patterns across decisions)
- `successful-patterns.md` / `failed-patterns.md` = aggregate signals (recurring traits, not individual products)

## 8. Notion Schema Overview

**Database:** Product Tracker
**Location:** MOVARO HQ → 📦 Product Research → Product Tracker
**Data source ID:** `35b53ba8-196e-8006-83fc-000bd9676ed9`

### Field Categories

**Agent fills — every product:**
Title, Score, Recommendation, Category, Price, Price Range, Saturation, Competitor Signal, Ad Platform, Source, Discovery Keyword, Emotional Trigger, Creative Angles, Ad Link, Store Link, Date Added, Status, Notes

**Agent fills — conditional:**
Rejection Reason (only when Founder Review = Rejected, set by Marina)
Supplier, Supplier Link, Social Link (hidden in Inbox view)
Problem Solved, Why It May Work (hidden in Inbox view)

**Marina fills — always blank when agent saves:**
Founder Review (Approved / Consider / Rejected)
Founder Notes
Test Status, CTR, CPM

### Recommendation vs Founder Review

| Field | Owner | Values | Meaning |
|-------|-------|--------|---------|
| Recommendation | Agent | Worth Testing / Needs Verification / Rejected | AI evaluation |
| Founder Review | Marina only | Approved / Consider / Rejected | Human decision |

These fields are independent. A product can be:
- Recommendation: Worth Testing + Founder Review: (blank) → agent scored it, Marina hasn't reviewed
- Recommendation: Worth Testing + Founder Review: Rejected → agent liked it, Marina rejected it
- Recommendation: Rejected + Founder Review: (blank) → agent rejected, Marina may confirm later

### Competitor Signal Values

| Value | Market Stage | Action |
|-------|-------------|--------|
| None | No ads found | Higher risk — organic signals only |
| Testing | New ads, early stage | Watch — may be emerging |
| Scaling | Active ads, recent, growing | **Enter — sweet spot** |
| Saturated | 100+ active ads, many brands | Too late |
| Legacy Winner | Long-running dominant campaigns | Do not enter |

### Three Notion Views

| View | Location | Filter | Visible Columns | Sort |

| `💡 Intelligence` | 📦 Product Research page (linked view) | Founder Review = Approved OR Consider | All columns | Score ↓ |

## 9. Memory Anti-Duplication Rules

Three levels of deduplication:

### Level 1 — Cross-session dedup (product level)
- **File:** `memory/reported-products.md`
- **When:** Step 0 of every session
- **Rule:** If product name appears in the log → skip entirely, do not re-evaluate

### Level 2 — Advertiser/store dedup (Facebook scraper)
- **File:** `memory/seen-advertisers.md`
- **When:** Scraper runs with `--seen=memory/seen-advertisers.md`
- **Rule:** If store domain matches any entry → scraper skips the ad automatically

### Level 3 — Pattern-level dedup (calibration)
- **Files:** `memory/rejected-products.md`, `memory/failed-patterns.md`
- **When:** Before scanning (Step 0)
- **Rule:** If a new candidate matches a known failure pattern → reject fast without scoring

### Memory Update Rules (end of session — mandatory)
1. `memory/reported-products.md` — add every product scored 65+
2. `memory/rejected-products.md` — add notable rejections only (non-obvious reasons, teachable failures)
3. `memory/successful-patterns.md` — add only if NEW pattern discovered (do not repeat existing entries)
4. `memory/failed-patterns.md` — add only if NEW failure pattern confirmed
